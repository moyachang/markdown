### 1. 何時會用到？及用它的必要性？
* **使用時機：** 在 **Spring Data JPA** 中，使用**原生 SQL（`nativeQuery = true`）**搭配 **`Page<T>` 進行分頁查詢**，且 SQL 語法較複雜（例如包含 `JOIN`、`GROUP BY`、子查詢、CTE 語法）時。
* **必要性：** 
  * **避免系統報錯：** 遇到複雜的 Native SQL 時，Spring 內建自動產生的 `COUNT` 語法常常會解析失敗、導致執行時期直接拋出 SQL 語法錯誤（Syntax Error）。
  * **救回查詢效能：** 自動產生的計數語法有時會把整段複雜邏輯包成子查詢再算總數，造成資料庫效能極差；手動寫能大幅縮短查詢時間。

---

### 2. 簡單的範例
假設我們要分頁查詢「特定狀態的用戶」，且主查詢有搭配 `LEFT JOIN` 與排序：

```java
public interface UserRepository extends JpaRepository<User, Long> {

    @Query(
        // 1. 實際撈取當頁資料的 SQL
        value = "SELECT u.* FROM users u " +
                "LEFT JOIN orders o ON u.id = o.user_id " +
                "WHERE u.status = :status " +
                "ORDER BY u.created_at DESC",
                
        // 2. 專門用來算總筆數的 SQL（拿掉了不需要的 JOIN 與 ORDER BY）
        countQuery = "SELECT COUNT(1) FROM users u WHERE u.status = :status",
        
        nativeQuery = true
    )
    Page<User> findUsersByStatus(@Param("status") String status, Pageable pageable);
}
```

---

### 3. 撰寫的重點為何？
* **拿掉 `ORDER BY`：** 算總筆數不需要排序，移除它可省去資料庫額外排序的效能消耗（在 Oracle 中子查詢包含 `ORDER BY` 也容易引發效能或語法問題）。
* **精簡無關的 `JOIN`：** 若 `LEFT JOIN` 只是為了撈取顯示欄位、不影響篩選條件，在 `countQuery` 中直接刪除該關聯。
* **注意 `GROUP BY` 的陷阱：** 若主查詢有 `GROUP BY`，`countQuery` 不能直接寫 `SELECT COUNT(*)`（這會變成算出每個群組各自的筆數），而應該改用 `SELECT COUNT(DISTINCT 欄位)` 或外層包一層 `SELECT COUNT(1) FROM (原查詢)`。
* **參數名稱必須一致：** `countQuery` 內使用的查詢條件參數（例如 `:status`），名稱與型別必須與 `value` 中的主查詢完全對應。

---

### 4. Oracle 也適用嗎？
* **完全適用，而且在 Oracle 專案中非常實用！**
* Spring Data JPA 底層會根據你設定的 Oracle Dialect（方言），自動把 `value` 加上分頁語法（舊版用 `ROWNUM`，Oracle 12c 以上用 `OFFSET ... FETCH NEXT ... ROWS ONLY`），並同時獨立執行你寫的 `countQuery`。
* **Oracle 撰寫小提醒：** 寫 Oracle 的 `countQuery` 時，結尾**千萬不要加分號（`;`）**，否則透過 JDBC 執行時會報 `ORA-00911: invalid character`（無效字元）錯誤。
