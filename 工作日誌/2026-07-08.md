這是個很經典的「樹狀結構 CRUD + 異動追蹤」問題。核心困難點有兩個：一是巢狀 JSON 要攤平回關聯式資料表（ROL / ROL_MEM 兩張表、還有 PARENT_ID 自我參照），二是要能精準知道「哪些節點變了、怎麼變的」以便寫入異動紀錄。以下是建議的設計方向。

## 1. 先解決「怎麼知道哪裡變了」——Diff 策略

有兩種做法，優缺點不同：

**方案 A：前端全量回傳，後端做 Diff（推薦）** 前端把整棵樹（不管有沒有異動）完整送回，後端撈出 DB 現有資料，兩邊做比對算出差異。

- 優點：前端邏輯簡單，不用自己追蹤操作歷程；後端是真實資料的守門員，比較不會被前端狀態污染。
- 缺點：搬移節點（換 PARENT_ID）、排序異動，比對邏輯會稍微複雜。

**方案 B：前端標記操作，送出 Change Set** 前端在使用者操作當下就記錄每個節點的動作（`_action: "add" | "update" | "delete" | "move"`），只送真正有異動的節點（含其 parentId）。

- 優點：後端不用自己算 diff，異動類型明確。
- 缺點：依賴前端狀態管理要做得很紮實，且如果前端 bug 漏標記，後端很難自己抓出來。

**建議混合**：前端送整棵樹（方案 A 的資料），但每個節點額外帶一個**前端本地產生的 tempId 標記新節點**（例如 `NEW_uuid` 或 `isNew: true`），這樣「新增」一眼就能判斷，其餘（update/delete/move）交給後端跟 DB snapshot 比對，兼顧簡單與可靠。

## 2. 攤平樹狀結構

不管哪種方案，第一步都是把巢狀 JSON 轉成扁平清單，方便對照兩張表：

```
function flatten(node, parentId, projectId, result) {
  result.rol.push({
    projectId, rolId: node.rolId, rolName: node.name, parentId
  });
  for (emp of node.employees) {
    result.rolMem.push({
      projectId, rolId: node.rolId, memId: emp.memId, memType: emp.memType
    });
  }
  for (child of node.orgs) {
    flatten(child, node.rolId, projectId, result); // 遞迴，parentId 帶入自己的 rolId
  }
}
```

攤平後你會得到兩個 list：`newRolList`、`newRolMemList`，這就是「這次前端送來的最終狀態」。

## 3. 後端 Diff 邏輯

```
oldRolList    = SELECT * FROM UP4_PROJECT_ROL WHERE PROJECT_ID = :pid
oldRolMemList = SELECT * FROM UP4_PROJECT_ROL_MEM WHERE PROJECT_ID = :pid

# 用 rolId / (rolId+memId+memType) 當 key 做 Map 比對
toInsert = newList 中 key 不存在於 oldList
toUpdate = 兩邊都存在但欄位值不同（name 變了、parentId 變了）
toDelete = oldList 中 key 不存在於 newList
```

ROL_MEM 因為是複合鍵（沒有自己的 PK，是 PROJECT_ID+ROL_ID+MEM_ID+MEM_TYPE 組合），比較單純，用 key 存在與否判斷即可（人員異動通常沒有「update」，只有加入/移除）。

ROL 這張因為有 PARENT_ID，要特別注意：**「搬移節點」在 diff 上會被判定成 update（PARENT_ID 欄位不同），這其實是正確的**，異動紀錄上可以特別標註「結構變更（搬移）」而不是單純的「改名」。

## 4. 交易與寫入順序

用 DB Transaction 包起來，且要注意順序：

1. **Insert** 新的 ROL（若有子節點掛在新節點下，要先插入父節點才能滿足 FK）
2. **Update** 有異動的 ROL（含 PARENT_ID 搬移）
3. **Delete** 被刪除的 ROL —— 這裡要考慮「整個子樹被刪除」的情況，通常前端把父節點刪掉，子節點在新 tree 裡也會一併消失，所以子孫節點也要一起被判定為 toDelete（可以用 cascade delete，或在 diff 時遞迴標記整個子樹）
4. ROL_MEM 的 insert/delete

```sql
BEGIN TRAN;
  -- 依序執行 insert/update/delete
  -- 若失敗整個 rollback，異動紀錄也不寫
COMMIT;
```

## 5. 異動紀錄設計

建議另建一張 Log 表，例如 `UP4_PROJECT_ROL_LOG`：

|欄位|說明|
|---|---|
|LOG_ID|PK|
|PROJECT_ID|專案 ID|
|ROL_ID|職務 ID|
|ACTION_TYPE|ADD / UPDATE / DELETE / MOVE|
|FIELD_NAME|異動欄位（如 ROL_NAME、PARENT_ID）|
|OLD_VALUE / NEW_VALUE|異動前後值|
|OPERATOR|操作人|
|OPERATE_TIME|時間|

**兩種紀錄粒度可選：**

- **欄位級**：像上表，一筆記錄對應一個欄位變化，適合要顯示「XX 把職務名稱從 A 改成 B」這種細緻歷程。
- **記錄級（Snapshot）**：直接把整個節點變動前後的 JSON 存進 `OLD_SNAPSHOT` / `NEW_SNAPSHOT`（存成 nvarchar(max) JSON），適合只是要「能回溯查看某時間點整包資料長怎樣」，不需要逐欄位比對，實作也簡單很多。

如果你們的異動紀錄需求只是「稽核用、偶爾人工回頭查」，我會建議用 Snapshot 方式，開發成本低很多；如果要在畫面上做出像 Git diff 那種「哪個欄位被誰改成什麼」，才值得做到欄位級。

## 6. 整體流程總結

```
前端送出完整樹(含新節點 tempId 標記)
   ↓
後端攤平成 flat list (ROL / ROL_MEM)
   ↓
後端撈出 DB 現況，做 diff (insert/update/delete)
   ↓
BEGIN TRANSACTION
   依序寫入 ROL / ROL_MEM 的異動
   同步寫入異動紀錄 LOG 表
COMMIT
   ↓
回傳最新樹給前端（新節點的正式 rolId 要換掉前端的 tempId）
```

有一點特別提醒:新增節點時，前端給的 tempId 不會是真正的 `ROL_ID`（畢竟真正的 ID 格式如 `ROL005687` 應該是後端產生的），所以 response 一定要把 tempId → 正式 ID 的對照表回傳給前端，前端才能更新畫面上的節點狀態，避免下次操作又把它當「新節點」重複新增。

你們目前資料量大概多大（職務階層深度、單一專案節點數量）？如果量不大，方案 A（後端全量 diff）會是最單純可靠的做法；如果階層很深、操作很頻繁，可能要考慮做局部更新 API（例如「只搬移單一節點」的專屬 endpoint）減少每次都要整棵樹比對的成本。

好的，用 Java（假設 Spring Boot + JPA/MyBatis）的角度來說明。

## 一、DB 撈出來的 Flat List → 建成樹狀結構

這是回傳給前端時最核心的邏輯。**關鍵技巧：先用 Map 建索引，再一次遍歷組裝親子關係，時間複雜度 O(n)，千萬不要遞迴查詢 DB（會有 N+1 問題）。**

### 1. Entity / DTO 設計

```java
// DB Entity（對應 UP4_PROJECT_ROL）
@Entity
@Table(name = "UP4_PROJECT_ROL")
public class ProjectRolEntity {
    @Id
    private String rolId;
    private String projectId;
    private String rolName;
    private String parentId;
    // getter/setter
}

// DB Entity（對應 UP4_PROJECT_ROL_MEM）
@Entity
@Table(name = "UP4_PROJECT_ROL_MEM")
public class ProjectRolMemEntity {
    private String projectId;
    private String rolId;
    private String memId;
    private String memType; // ORG, PTS, PTM
    // 複合鍵可用 @EmbeddedId 或 @IdClass
}

// 回傳給前端的樹狀 DTO
public class RolTreeNode {
    private String treeId;      // 對應圖1的 treeId，通常 = rolId
    private String rolId;
    private String name;
    private List<EmployeeDTO> employees = new ArrayList<>();
    private List<RolTreeNode> orgs = new ArrayList<>();
    
    // 這個欄位不進DB，純粹讓前端好比對用，下面會解釋
    private String parentId; 
}

public class EmployeeDTO {
    private String treeId;   // rolId + "_" + memId，圖1範例的組合方式
    private String memId;
    private String memType;
    private String name;
    private String avatar;
    private String orgPathName;
    private String orgPathId;
}
```

### 2. 建樹演算法（Service 層）

```java
public List<RolTreeNode> buildTree(String projectId) {
    List<ProjectRolEntity> rolList = rolRepository.findByProjectId(projectId);
    List<ProjectRolMemEntity> memList = rolMemRepository.findByProjectId(projectId);

    // Step 1: 依 rolId 分組員工，方便掛載
    Map<String, List<EmployeeDTO>> memMapByRolId = memList.stream()
        .map(this::toEmployeeDTO)
        .collect(Collectors.groupingBy(EmployeeDTO::getRolIdRef)); 
        // rolIdRef 是掛載用的暫存欄位，不會序列化出去

    // Step 2: 把每個 ROL 轉成 TreeNode，並用 Map 存起來（key = rolId）
    Map<String, RolTreeNode> nodeMap = new LinkedHashMap<>();
    for (ProjectRolEntity rol : rolList) {
        RolTreeNode node = new RolTreeNode();
        node.setTreeId(rol.getRolId());
        node.setRolId(rol.getRolId());
        node.setName(rol.getRolName());
        node.setParentId(rol.getParentId());
        node.setEmployees(memMapByRolId.getOrDefault(rol.getRolId(), new ArrayList<>()));
        nodeMap.put(rol.getRolId(), node);
    }

    // Step 3: 掛父子關係
    List<RolTreeNode> roots = new ArrayList<>();
    for (RolTreeNode node : nodeMap.values()) {
        String parentId = node.getParentId();
        if (parentId == null || !nodeMap.containsKey(parentId)) {
            roots.add(node); // 沒有父節點 = 根節點
        } else {
            nodeMap.get(parentId).getOrgs().add(node);
        }
    }
    return roots;
}
```

這樣一次查詢（其實是兩條 SQL：查 ROL、查 ROL_MEM，各一次，不管深度多深都不會多次 call DB）就能組出完整的樹。**這是最推薦的方式**，效能穩定可預期。

> 補充：如果資料庫階層深度可能很深、節點數很多，可以在 `rolId` 上加 index（`parentId` 也建議加 index，因為上面 groupingBy/查詢常會用到）。

## 二、前端傳回的樹 → Diff → 存回 DB

### 1. 先攤平（遞迴）

```java
public class FlattenResult {
    List<ProjectRolEntity> rolList = new ArrayList<>();
    List<ProjectRolMemEntity> memList = new ArrayList<>();
}

private void flatten(RolTreeNode node, String parentId, String projectId, FlattenResult result) {
    ProjectRolEntity rol = new ProjectRolEntity();
    rol.setProjectId(projectId);
    rol.setRolId(node.getRolId());
    rol.setRolName(node.getName());
    rol.setParentId(parentId);
    result.rolList.add(rol);

    for (EmployeeDTO emp : node.getEmployees()) {
        ProjectRolMemEntity mem = new ProjectRolMemEntity();
        mem.setProjectId(projectId);
        mem.setRolId(node.getRolId());
        mem.setMemId(emp.getMemId());
        mem.setMemType(emp.getMemType());
        result.memList.add(mem);
    }

    for (RolTreeNode child : node.getOrgs()) {
        flatten(child, node.getRolId(), projectId, result); // 遞迴往下
    }
}
```

### 2. Diff（用 Map 比對，Java Stream 寫起來很自然）

```java
@Transactional
public void saveTree(String projectId, List<RolTreeNode> newTree, String operator) {

    // 1. 攤平前端送來的資料
    FlattenResult newData = new FlattenResult();
    for (RolTreeNode root : newTree) {
        flatten(root, null, projectId, newData);
    }

    // 2. 撈出 DB 現況
    List<ProjectRolEntity> oldRolList = rolRepository.findByProjectId(projectId);
    Map<String, ProjectRolEntity> oldRolMap = oldRolList.stream()
        .collect(Collectors.toMap(ProjectRolEntity::getRolId, r -> r));
    Map<String, ProjectRolEntity> newRolMap = newData.rolList.stream()
        .collect(Collectors.toMap(ProjectRolEntity::getRolId, r -> r));

    List<ChangeLog> logs = new ArrayList<>();

    // 3. Insert：新 map 有、舊 map 沒有
    for (String rolId : newRolMap.keySet()) {
        if (!oldRolMap.containsKey(rolId)) {
            rolRepository.save(newRolMap.get(rolId));
            logs.add(ChangeLog.of(projectId, rolId, "ADD", null, null, null, operator));
        }
    }

    // 4. Update：兩邊都有，但欄位不同
    for (String rolId : newRolMap.keySet()) {
        if (oldRolMap.containsKey(rolId)) {
            ProjectRolEntity oldRol = oldRolMap.get(rolId);
            ProjectRolEntity newRol = newRolMap.get(rolId);

            if (!Objects.equals(oldRol.getRolName(), newRol.getRolName())) {
                logs.add(ChangeLog.of(projectId, rolId, "UPDATE", "ROL_NAME",
                    oldRol.getRolName(), newRol.getRolName(), operator));
            }
            if (!Objects.equals(oldRol.getParentId(), newRol.getParentId())) {
                logs.add(ChangeLog.of(projectId, rolId, "MOVE", "PARENT_ID",
                    oldRol.getParentId(), newRol.getParentId(), operator));
            }
            rolRepository.save(newRol); // JPA 會依 PK 自動判斷 update
        }
    }

    // 5. Delete：舊 map 有、新 map 沒有
    for (String rolId : oldRolMap.keySet()) {
        if (!newRolMap.containsKey(rolId)) {
            rolRepository.deleteById(rolId);
            logs.add(ChangeLog.of(projectId, rolId, "DELETE", null, null, null, operator));
        }
    }

    // 6. ROL_MEM 用同樣邏輯（複合 key 用字串組合當 Map key）
    diffAndSaveMem(projectId, oldRolList, newData.memList, logs, operator);

    // 7. 寫入異動紀錄
    changeLogRepository.saveAll(logs);
}
```

`@Transactional` 是這裡的重點——只要 insert/update/delete/log 任何一步例外，Spring 會自動 rollback 整包，不會出現「刪了一半、log 沒寫」的髒資料狀態。

### 3. 「刪除父節點時，子孫要一併判定刪除」怎麼處理？

其實**不用特別處理**——因為前端如果刪掉某個父節點，回傳的新樹裡子孫節點自然就不存在了，攤平出來的 `newRolMap` 就不會有那些 rolId，diff 時自動被判定成 DELETE。這也是「送整棵樹」這個方案的優點之一：子樹刪除是自然而然發生的，不用額外寫遞迴刪除邏輯。

如果擔心 FK 約束（父節點被刪但子節點還沒刪，順序衝突），可以：

- 用 `ON DELETE CASCADE`（DB 層級自動處理）
- 或在程式碼裡先刪子節點再刪父節點（依樹的深度排序）

### 4. 新節點的 ID 產生與回傳

```java
// 新節點前端傳來的 rolId 可能是暫時值，例如 "NEW_1"
```

## 三、後端傳給前端的樹狀結構建議

延續你圖1的格式，我建議維持「單一遞迴節點格式」，但補強幾個實務上會用到的欄位：

```json
{
  "treeId": "ROL005687",
  "rolId": "ROL005687",
  "parentId": null,
  "name": "專案負責人",
  "employees": [
    {
      "treeId": "ROL005687_MEM123",
      "memId": "MEM123",
      "memType": "org",
      "name": "湯川風",
      "avatar": "...",
      "orgPathName": "主管-企業管理部-A公司",
      "orgPathId": "ROL005687-DEP00123-company"
    }
  ],
  "orgs": [
    {
      "treeId": "ROL009231",
      "rolId": "ROL009231",
      "parentId": "ROL005687",
      "name": "專案經理",
      "employees": [ "..." ],
      "orgs": [ "..." ]
    }
  ]
}
```

**幾個設計建議：**

1. **`treeId` 保持跟 `rolId` 一致**（不要另外造一套 ID 體系），減少前端維護兩套 ID 對照的複雜度。目前圖1的員工節點用 `rolId_memId` 組合當 treeId，這個做法沒問題，因為同一個 memId 理論上可能掛在不同職務下，需要用複合 ID 保證前端 React/Vue 的 key 唯一性。
    
2. **補上 `parentId` 欄位**（雖然巢狀結構本身已經表達父子關係），原因是：
    
    - 前端做「拖曳搬移節點」功能時，直接改 `parentId` 比重組整個巢狀陣列簡單很多；
    - 送回後端時，你也可以選擇不送巢狀結構，而是送一份 flat list（附 parentId），這樣後端甚至不用自己攤平，直接拿去 diff，減少一層轉換。
    
    這其實引出一個值得考慮的替代方案：**前端與後端之間乾脆直接用 flat list + parentId 溝通**，只有「畫面渲染」那一層前端自己用 parentId 現場組樹（前端組樹用 JS 也是幾行 code）。這樣後端完全不用寫巢狀 ↔ 攤平的轉換邏輯，維護起來更單純。是否要這樣做，取決於前端團隊的偏好。
    
3. **加一個 `version` 或 `updatedAt` 欄位在最外層**（非必要但建議），用於「樂觀鎖」（Optimistic Lock）：如果 A、B 兩人同時打開同一個專案樹編輯，A 存檔後，B 再存檔時後端可以比對 version 不一致而拒絕，避免覆蓋別人的異動。這在多人協作的樹狀編輯場景中很常遇到。
    
4. **員工節點是否該放巢狀裡，還是拉平成獨立陣列？** 目前放在巢狀節點內（跟著 orgs 一起送），對前端渲染樹狀圖是方便的。但如果之後有「同一個人跨多個職務」或需要「員工總覽列表」的需求，可以額外開一支 API 單獨查詢，不需要動這個樹狀 API 的結構。

## 問題 1：前端搬移節點時，是自己改 parentId 嗎？後端怎麼比對？

對，是這個意思。舉例：使用者在畫面上把「專案經理」這個節點，從掛在「專案負責人」底下，拖曳改成掛在「技術總監」底下。

如果資料是**巢狀結構**，前端要做的事情是：

1. 把該節點物件從原本父節點的 `orgs` 陣列裡移除
2. 把它塞進新父節點的 `orgs` 陣列裡
3. 同時把該節點的 `parentId` 欄位值改成新父節點的 rolId（這一步是我建議加的，純粹是資料一致性，不影響巢狀結構本身）

也就是說，**巢狀結構的「位置」本身就代表了父子關係**，`parentId` 欄位在這裡其實是「冗餘資訊」——理論上不需要，但實務上加了會讓前端邏輯更好寫（尤其是搬移時，直接改一個欄位值，比操作陣列插入/移除更不容易出 bug），也讓後端 debug 時方便肉眼確認。

**後端怎麼比對？** 不管前端傳巢狀還是 flat，後端拿到資料後第一步都是**攤平**（如果是巢狀，遞迴攤平時用「當前遍歷到的父節點 rolId」寫入子節點的 parentId；如果本來就是 flat，直接拿現成的 parentId 欄位）。攤平完之後兩種來源結果一樣，都是：

```
rolId=ROL009231, parentId=ROL_技術總監ID  ← 新的
```

跟 DB 原本存的：

```
rolId=ROL009231, parentId=ROL005687(專案負責人)  ← 舊的
```

一比對，`parentId` 不一樣 → 判定為 MOVE，寫入異動紀錄。**所以不管前端傳哪種格式，後端的 diff 邏輯完全一樣**，因為 diff 永遠是在攤平之後的 flat 資料上做比較，這一步是無法避免的。

## 問題 2：後端傳巢狀、前端傳 flat，前端不是還要自己重組嗎？

你抓到重點了，這確實是我上次沒講清楚的地方——我把「畫面渲染需要的格式」跟「跟後端溝通的格式」混在一起講了。拆開來看：

||巢狀 (Nested)|攤平 (Flat + parentId)|
|---|---|---|
|**畫面渲染樹狀圖**|直接可用（tree 元件通常吃巢狀資料）|需要前端自己組一次樹|
|**傳給後端存檔**|後端要攤平|後端不用攤平，直接比對|

如果後端回傳巢狀、前端存檔時卻要傳 flat，那前端等於要做一次「巢狀 → 攤平」的轉換，只是把攤平這個工作**從後端搬到前端**而已，並沒有真的減少工作量，只是換人做而已。這確實不划算，除非有特別理由（例如前端本來就用 flat 資料 + 某個 library 在做樹狀渲染，內部已經是 flat 狀態，順手傳出去反而更省事）。

**所以我修正一下建議：除非前端团隊明確表示他們內部狀態管理本來就是 flat（例如用某些 tree UI library，它們狀態本身就是攤平陣列），否則沒必要為了「省後端一次遍歷」而讓前端多做一次轉換。攤平這個動作，不管在哪一端做，都是逃不掉的，交給後端做（用遞迴，程式碼量很小）反而最省事，因為：**

1. 後端本來就要為了 diff 而攤平，這一步無論如何都要寫
2. 前端維持巢狀來回傳輸，畫面渲染邏輯最單純，不用維護兩套資料形狀
3. 減少一端要做格式轉換的機會，就減少一種出錯可能

## 結論：維持你原本圖1的巢狀格式即可

- **後端回傳**：巢狀（如圖1），每個節點補上 `parentId` 欄位（純粹方便前端搬移時改值、也方便肉眼 debug，不影響結構本身）
- **前端操作**：搬移時，同步改該節點的 `parentId` 值 + 調整巢狀陣列位置（這兩件事其實可以只做「調整巢狀陣列位置」，`parentId` 由前端在送出前，用跟後端一樣的攤平邏輯自動算出來，不用手動維護兩份真相來源，減少不同步風險）
- **前端送出**：一樣傳巢狀結構回後端
- **後端接收**：攤平 → diff → 存檔 + log

這樣前後端只有一種資料格式要維護，我上次提的「flat 溝通」那個方案，除非有明確效能或前端框架的理由，不然建議捨棄，單純增加複雜度而已，抱歉上次沒講清楚利弊。
