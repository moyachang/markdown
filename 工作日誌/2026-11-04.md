`@Builder` 的判斷重點是：**建立物件時，用欄位名稱逐一指定值，是否會比建構子更清楚？**

以你現在的 DDD + Clean 專案來說，**不用每個類別都加**。

例如這種建構子：

```
new MemberInfo(
    memId, memName, avatar, rolId, rolName,
    orgPathId, orgPathName, isPartner
);
```

參數很多，又有很多 `String`，容易放錯位置。這時加 `@Builder` 就很適合：

```
MemberInfo.builder()
        .memId(memId)
        .memName(memName)
        .avatar(avatar)
        .rolId(rolId)
        .rolName(rolName)
        .orgPathId(orgPathId)
        .orgPathName(orgPathName)
        .isPartner(isPartner)
        .build();
```

雖然比較長，但每個值的用途更清楚。

|情況|是否適合加|
|---|---|
|只有兩三個參數，意思清楚|通常不需要|
|參數很多，尤其多個相同型別|適合|
|有許多選填欄位|適合|
|Response DTO、查詢結果物件，需要手動組裝很多欄位|適合|
|主要交給 MapStruct 等工具建立，手寫呼叫很少|不必為了它特別加|
|Spring Service、Controller 等注入元件|通常不需要，用建構子注入|
|Domain Entity、Aggregate|先考慮業務規則，再決定|
|JPA Entity|可以使用，但要配合 JPA 的建構子要求|

**你最需要注意的是：`@Builder` 不會自動保證必填，也不會檢查業務規則。**

例如：

```
MemberInfo.builder().build();
```

如果沒有另外驗證，參考型別通常就會是 `null`，基本型別則是 `false`、`0` 等預設值。

因此，像「建立任務時，名稱不可空白」這類 Domain 規則，應該放在建構子或工廠方法裡：

```
public static ProjectTask create(String name, String parentId) {
    if (name == null || name.isBlank()) {
        throw new IllegalArgumentException("任務名稱不可空白");
    }

    return new ProjectTask(name, parentId);
}
```

如果參數很多，仍然想使用 Builder，可以**把 `@Builder` 放在有驗證的建構子上**，讓 `build()` 經過同一套檢查。

對你而言，可以先採用這個原則：**欄位多、需要手動組裝的 DTO 優先考慮 `@Builder`；Domain 物件先設計建立規則；Service 用建構子注入。**
