# 有可能公用的 table，會需要建立哪些東西?

## 1. Entity (實體類別)
- **檔名命名規範：** `{TableName}Entity.java`（例如：`LaleLoginMappingJpaEntity.java`）
    
- **核心責任：** **ORMapping (物件關聯對映)**
    
- **主要用途：**
    
    - 直接對應資料庫中的 **資料表 (Table)** 與 **欄位 (Columns)**。
        
    - 透過 Jakarta Persistence 註解（如 `@Entity`, `@Table`, `@Id`, `@Column`）宣告主鍵、欄位長度、是否允許 Null 等綱要屬性。
        
    - 作為 JPA 底層與資料庫進行 `INSERT` / `UPDATE` / `SELECT` 互動時的核心資料物件。
    - 
## 2. Repository (資料存取介面)
- ==在 Clean Architec 裡，又會分開處理, 分成以下兩種==
	核心目的在於 **「解耦（Decoupling）」**——將系統的**核心商業邏輯（Domain Layer）** 與底層的 **資料庫技術框架（Spring Data JPA）** 完全隔離開來.
	- `SpringDataLaleEimLoginMappingRepository`
		 命名上直接寫 `SpringData` 開頭,是為了**明確標示「這是 Spring Data JPA 的東西」**,跟 domain 的介面做區隔,避免搞混。它就是直接繼承 `JpaRepository` 的介面,Spring 會自動生成實作。
		- **角色：** **Spring Data JPA 專用介面 (Infrastructure Layer)**
    	- **職責：**				    
		    - 繼承 Spring 的 `JpaRepository<Entity, ID>`。		        
		    - 負責處理任何與 Spring Data JPA 直接相關的底層語法、派生查詢（Derived Queries）或原生 SQL/JPQL。		        
		- **特性：** 這個介面強依賴於 Spring Data JPA 框架與 ORM Entity（例如 `LaleLoginMappingEntity`）。
		
    - `JpaLaleEimLoginMappingRepositoryAdapter` (轉接器 / 實作類別)
	     命名用 `Adapter` 結尾,這其實是在呼應**六角架構(Hexagonal Architecture / Ports & Adapters)**的術語——domain 定義的介面叫 **port**,而實作這個 port、去對接外部技術(這裡是 JPA)的類別就叫 **adapter**。這名字取得比我之前用的 `XxxRepositoryImpl` 更精確,直接點出「這是一個轉接器」的角色。
		- **角色：** **設計模式中的 Adapter（轉接器）(Infrastructure Layer)**
		- **職責：**
		       - **實作 Domain 層定義的 Repository 介面**（例如 `LaleEimLoginMappingRepository`）。
			- 內部注入（Inject）上面的 `SpringDataLaleEimLoginMappingRepository` 來真正執行 DB 讀寫。
		    - **負責 Domain Model 與 JPA Entity 之間的物件轉換**（如 `toDomain()` / `toEntity()`）。
		- **特性：** 它是連接核心商業邏輯與底層 DB 的橋樑。
		- 它在內部，可以進行 toDomainEntity、或者是 toJpaEntity 的轉換。
		- 
## 3. DTO / Record (資料傳輸物件)
- **檔名命名規範：** `{TableName}Record.java` 或 `{TableName}DTO.java`（例如：`LaleLoginMappingRecord.java`）
    
- **核心責任：** **API / Service 層之間的資料傳輸與隔離**
    
- **主要用途：**
    
    - **解耦與安全性**：避免直接把 JPA Entity 暴露給前端 API 或跨服務傳遞，防止資料庫結構直接外露，也可避免循環引用（如 Jackson 序列化問題）。
        
    - **不可變性（Immutable）**：使用 Java `record` 建立不可變物件，提供安全的資料載體。
        
    - 如果你的 Domain Record 裡面寫了 `fromEntity(RolGenInfEntity entity)`： 👉 你的 Domain 層就**被迫去 import JPA Entity**，這就破壞了「Domain 層不依賴任何外部框架與 DB 結構」的核心原則！

| **做法**                    | **fromEntity() 寫在 Record 內** | **轉換放在 Adapter / Mapper (你看到的設計)** |
| ------------------------- | ---------------------------- | ---------------------------------- |
| **Domain 純潔度**            | ❌ 被 JPA Entity 污染            | ⭕ 100% 純粹 Java，不依賴 DB              |
| **職責歸屬**                  | ❌ Record 既要當資料，又要懂 DB Entity | ⭕ Record 只當資料，Adapter 負責對接 DB      |
| **符合 Clean Architecture** | ❌ 違反依賴倒置                     | ⭕ 完全符合                             |

## 其他資料補充
### 後綴（Suffix）通常用在哪裡？

在現代 Java 與 Clean Architecture 架構中，字尾後綴通常只會用於**跨層傳輸或特定技術元件**：

| **元件類型**                  | **是否加後綴**    | **範例**                             | **說明**                                                    |
| ------------------------- | ------------ | ---------------------------------- | --------------------------------------------------------- |
| **Domain Model / Entity** | ❌ **不加**     | `RolGenInf`, `User`, `Order`       | 代表核心業務物件本身，保持最純粹的業務名稱。                                    |
| **JPA ORM Entity**        | ⭕ 可加         | `RolGenInfEntity`                  | 專門與 DB Table 對映的類別，加 `Entity` 方便與 Domain 物件區隔。            |
| **Data Transfer Object**  | ⭕ 可加         | `RolGenInfDto`, `RolGenInfRequest` | 用於 API Controller 或跨系統傳遞資料的物件。                            |
| **Record (若當作 DTO 時)**    | ⭕ 可加 (視團隊規範) | `RolGenInfRecord`                  | 如果這個 record **只被當成 DTO 使用**，有些團隊會加 `Record` 或 `Dto` 以示區別。 |
