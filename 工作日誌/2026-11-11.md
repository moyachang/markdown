我先確認目前 service 與查詢實作，再整理成簡短的呼叫流程。


新增權限設定 `POST /new`，目前程式流程如下：

```text
Controller 接收 Request
    ↓
PermissionMapper：Request → Command
    ↓
AddPermissionSettingService：去重複、驗證 orgId
    ↓
Repository Adapter：建立 Entity 並儲存
    ↓
QueryPort Adapter：查詢完整資訊
    ↓
PermissionMapper：Result → Response
    ↓
回傳 ApiResponse.success(responses)
```

1. **接收與驗證輸入**
   `PermissionSettingController` 限定登入的 `Administrator` 呼叫。透過 `@Valid` 檢查 module、type、list 與 orgId 格式，再轉成 `AddPermissionSettingCommand`。

2. **檢查人員／職務是否存在**
   `AddPermissionSettingService` 先去除重複 orgId，再透過 `Up4ModuleAuthQueryPort` 批次查詢。任何 ID 不存在就拋出例外，停止新增。

3. **儲存權限**
   `JpaUp4ModuleAuthRepositoryAdapter` 將每個 orgId 組成 Entity，呼叫 `saveAllAndFlush()` 寫入 `UP4_MODULE_AUTH`。建立與更新時間由 JPA auditing 填入。

4. **取得完整回傳資訊**
   `JpaUp4ModuleAuthQueryPortAdapter` 呼叫 `findPermissionRows()`，取得姓名、部門、公司等資料，再補上成員名單與頭像，組成 `PermissionResult`。

5. **轉換回應**
   Controller 透過 mapper 轉成 `PermissionResponse`，包裝成 `ApiResponse` 回傳。Service 的新增與回查在同一個交易內。

**目前有一點需要注意：你現在的儲存程式已沒有「略過資料庫既有權限」的判斷。** Service 的 `distinct()` 只去除本次輸入的重複 ID，因此再次新增已存在的權限，仍可能撞到唯一約束；目前尚未符合註解中的「已存在不重複新增」。

### @Query 原生寫法
```sql
@Query(value = """  
    SELECT a.ID AS id, a.ORG_ID AS orgId, a.UPDATED_AT AS updatedAt,           names.name AS name, names.department AS department, names.company AS company    """ + FILTERED + """  
    ORDER BY      CASE WHEN :sort = 'updatedAt' AND :ascending = 1 THEN a.UPDATED_AT END ASC,      CASE WHEN :sort = 'updatedAt' AND :ascending = 0 THEN a.UPDATED_AT END DESC,      a.ID ASC    """, countQuery = "SELECT COUNT_BIG(*) " + FILTERED, nativeQuery = true)  
Page<PermissionRow> searchPermissions(  
    @Param("module") String module, @Param("type") String type,  
    @Param("scope") String scope, @Param("keyword") String keyword,  
    @Param("pattern") String pattern, @Param("sort") String sort,  
    @Param("ascending") int ascending, Pageable pageable);
```
這段程式碼是 Spring Data JPA 中非常經典、但也常讓人頭痛的「在 Native Query (原生 SQL) 中使用條件式排序與字串拼湊」的寫法。

  

為了讓你徹底看懂它在幹嘛，我們把它拆解成三個部分來解釋：

  

### 一、 核心架構拆解

#### 1. `@Query` 的結構與 `nativeQuery = true`

- `nativeQuery = true`：代表裡面寫的是**純粹的 SQL Server 資料庫語法**，而不是 JPA 的 JPQL。
    
      
    
- `countQuery`：因為有做分頁（`Page<...>`），Spring Data JPA 需要知道「總筆數」是多少才能算總頁數。這裡重複使用了 `+ FILTERED` 這段條件來計算總數。
    
      
    

#### 2. 神祕的變數 `+ FILTERED +`

- 這不是原生 SQL 的語法，而是 Java 的字串相加（String Concatenation）。
    
      
    
- 在這個 `@Query` 的上方或同一個 Class 裡，一定有一個宣告好的常數字串 `FILTERED`（內容大概長這樣：`FROM UP4_MODULE_AUTH a ... WHERE ...`），用來把長長的 `FROM`、`LEFT JOIN` 和 `WHERE` 條件拼進來。
    
      
    

#### 3. 令人頭痛的 `CASE WHEN` 排序法

SQL

```
ORDER BY
  CASE WHEN :sort = 'updatedAt' AND :ascending = 1 THEN a.UPDATED_AT END ASC,
  CASE WHEN :sort = 'updatedAt' AND :ascending = 0 THEN a.UPDATED_AT END DESC,
  a.ID ASC
```

- **為什麼要這樣寫？** 因為在 SQL 的原生語法中，**參數（如 `:sort`）通常只能用來代入「數值或字串值」，不能用來代入「欄位名稱」**。你無法寫出像 `ORDER BY :sort` 這種動態欄位的 SQL。
    
      
    
- **它的運作邏輯**：
    
      
    - 如果傳入的 `:sort` 是 `'updatedAt'` 且 `:ascending` 是 `1`（升冪），那麼符合條件的那一行會回傳 `a.UPDATED_AT`，並進行 `ASC` 排序；不符合條件的行則回傳 `NULL`。
        
          
        
    - 透過這種方式，繞過了 SQL 不能動態傳入欄位名稱的限制。
        
          
        

### 二、 為什麼這種寫法常被嫌棄？（潛在風險）

雖然它能動態排序，但它有兩個致命缺點：

  

1. **效能隱憂（Performance Trap）**： 在 `ORDER BY` 裡面寫 `CASE WHEN`，資料庫在排序時非常難去有效地使用索引（Index），當資料量一大，這支查詢的效能會變得非常差（容易造成 Table Scan）。
    
      
    
2. **擴充性極差**： 如果你今天想要多支援一個欄位排序（例如 `module` 或 `type`），你就必須在 `ORDER BY` 底下再手動多加好幾行 `CASE WHEN ... THEN a.MODULE END ASC/DESC`，程式碼會變得極度冗長且難以維護。
    
      
    

### 三、 實務上更好的替代方案是什麼？

如果你想擺脫這種醜陋又傷效能的 `CASE WHEN` 排序，在 Spring Data JPA / Hibernate 中，最專業的做法是**改用「動態 SQL 拼接（如 Specifications / Criteria API）」**，或是像我們前面提到的：**在 Java Service 層先做好白名單檢查，安全地把欄位名稱組好後，再傳入 Repository。**

``
在這支 SQL 查詢中，這幾個 `CROSS APPLY` 的角色非常有趣，它們跟前面的 `OUTER APPLY`（用來去資料庫找資料）不同，這裡的 `CROSS APPLY` **根本不是用來「抓表格資料」的，而是被當成「變數計算機 / 程式中繼站」來用。**

  
```sql
SELECT a.ID AS id, a.ORG_ID AS orgId, a.UPDATED_AT AS updatedAt,
       names.name AS name, disp.orgPath AS orgPath
FROM UP4_MODULE_AUTH a
LEFT JOIN Mem_GenInf m ON m.MemID = a.ORG_ID
OUTER APPLY (SELECT TOP (1) p.NAME, p.Path, p.IDPath FROM Org_Path p
    WHERE p.OrgID = COALESCE(m.MainRoleID, a.ORG_ID)) node
OUTER APPLY (SELECT TOP (1) p.Path FROM Org_Path p
    WHERE (p.OrgID = 'company' OR p.OrgID LIKE 'COM%')
      AND CHARINDEX('/' + p.OrgID + '/', '/' + node.IDPath + '/') > 0
    ORDER BY LEN(p.IDPath) DESC) com
CROSS APPLY (SELECT CASE WHEN m.MemID IS NULL
    THEN LEFT(node.Path, LEN(node.Path) - LEN(node.NAME) - 2)
    ELSE node.Path END AS path) target
CROSS APPLY (SELECT COALESCE(m.UserName, node.NAME, a.ORG_ID) AS name,
    CASE WHEN LEN(target.path) > LEN(com.Path)
        THEN SUBSTRING(target.path, LEN(com.Path) + 3, 4000) ELSE '' END AS path) names
OUTER APPLY (SELECT STRING_AGG(CAST(j.value AS nvarchar(4000)), N'-')
        WITHIN GROUP (ORDER BY CAST(j.[key] AS int) DESC) AS orgPath
    FROM OPENJSON(N'["' + REPLACE(STRING_ESCAPE(names.path, 'json'), N'>>', N'","') + N'"]') j
    WHERE names.path <> '') rev
CROSS APPLY (SELECT rev.orgPath AS orgPath,
    CASE WHEN rev.orgPath IS NULL THEN names.name
        ELSE CONCAT(names.name, N'【', rev.orgPath, N'】') END AS displayName) disp
WHERE a.MODULE = ? AND a.TYPE = ?
  AND (? = '' OR CHARINDEX('/' + ? + '/', '/' + node.IDPath + '/') > 0)
  AND (? = '' OR disp.displayName LIKE ? ESCAPE '!')
ORDER BY
  CASE WHEN ? = 1 THEN a.UPDATED_AT END ASC,
  CASE WHEN ? = 0 THEN a.UPDATED_AT END DESC,
  a.ID ASC offset 0 rows fetch first ? rows only
```
如果你仔細看這三個 `CROSS APPLY`（`target`、`names`、`disp`），它們的右側子查詢都沒有去 `FROM` 任何實體資料表，而只是在做數學運算、字串切割（`LEFT`、`SUBSTRING`）或條件判斷（`CASE WHEN`）。

  

為什麼工程師要大費周章用 `CROSS APPLY` 來做這件事？主要有以下兩個關鍵原因：

  

### 原因一：SQL 的「變數傳遞與管線化 (Pipeline)」限制

在標準 SQL 中，如果你在同一個 `SELECT` 裡面算了一個欄位（例如：`2 + 3 AS total`），你在**同一個查詢層級的後面**是沒辦法直接拿 `total` 來做下一步計算的，除非你包在子查詢或巢狀結構裡。

  

而 `CROSS APPLY` 提供了一個極佳的管道效果：

  

> **「上一段算出來的東西，可以直接當作變數餵給下一段使用，像寫程式碼一樣一條龍往下算。」**
> 
>   

我們來看這段漂亮的連鎖反應：

  

1. **第一步 (`node` / `com`)**：從資料庫撈出原始路徑。
    
      
    
2. **第二步 (`CROSS APPLY target`)**：拿 `node` 的結果去算出 `target.path`。
    
      
    
3. **第三步 (`CROSS APPLY names`)**：**直接拿上一步算出來的 `target.path`**，去跟 `com.Path` 做比對、切字串（`SUBSTRING`），算出乾淨的路徑與名稱。
    
      
    
4. **第四步 (`CROSS APPLY disp`)**：再拿前面算好的結果組合成最終的 `displayName`。
    
      
    

如果不用 `CROSS APPLY`，你就要寫出超級可怕、巢狀包了好幾層的 `CASE WHEN(CASE WHEN(...))`，可讀性會完全崩潰。

  

### 原因二：讓 `WHERE` 條件可以直接使用計算後的欄位

看最後一個 `CROSS APPLY (SELECT ... AS displayName) disp`：

  

SQL

```
CROSS APPLY (SELECT rev.orgPath AS orgPath,
    CASE WHEN rev.orgPath IS NULL THEN names.name
        ELSE CONCAT(names.name, N'【', rev.orgPath, N'】') END AS displayName) disp
...
WHERE ... 
  AND (? = '' OR disp.displayName LIKE ? ESCAPE '!')
```

這段的目的，是為了**在 `WHERE` 條件中能夠直接對 `disp.displayName` 進行關鍵字搜尋 (`LIKE`)**。

  

在 SQL 的執行順序中，`WHERE` 執行的時間點比 `SELECT` 的欄位別名還要早。如果不用 `APPLY` 或子查詢把 `displayName` 先算出來，你在 `WHERE` 裡面是不能直接寫 `WHERE displayName LIKE ...` 的（資料庫會報錯說找不到這個欄位）。`CROSS APPLY` 提前把這個欄位「具象化」了，讓後面的 `WHERE` 與 `ORDER BY` 可以直接拿來用。

  

### 💡 為什麼這裡用 `CROSS APPLY` 而不是 `OUTER APPLY`？

因為這幾個 `CROSS APPLY` 裡面執行的都只是簡單的邏輯判斷（`CASE WHEN`、`SUBSTRING`），**它們保證會回傳剛好一筆計算結果**，不會像去查資料表那樣可能回傳空集合（0 筆）。

  

既然絕對不會是空集合，用 `CROSS APPLY`（相當於 INNER JOIN 的概念）就不會導致資料遺失，反而最安全直接。
