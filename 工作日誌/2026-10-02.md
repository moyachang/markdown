針對您提出的三個問題，以下為逐一詳細解答：

  

### 1. Annotation 各自的作用與必要性檢視

#### **Lombok 註解**

- **`@Data`**：自動生成所有欄位的 getter、setter、`equals()`、`hashCode()` 與 `toString()`。
    
      
    - **必要性**：**建議替換**。在 JPA Entity 上直接使用 `@Data` 會自動生成 `equals()` 與 `hashCode()`，若 Entity 內部有關聯屬性（如 `@ManyToOne`），容易引發無窮迴圈或效能問題。實務上 JPA Entity 建議改用 **`@Getter`** 與 **`@Setter`** 即可。
        
          
        
- **`@Builder`**：提供 Builder 建造者模式（如 `Up4ProjectTaskMemJpaEntity.builder()...build()`），方便建立物件。
    
      
    - **必要性**：非必須，但**非常建議保留**，能在測試或建構物件時寫出很乾淨的程式碼。
        
          
        
- **`@NoArgsConstructor`**：生成無參數建構子。
    
      
    - **必要性**：**完全必須**。JPA 規範要求所有的 Entity 必須有一個無參數建構子，以便在從資料庫反序列化物件時透過反射建立實體。
        
          
        
- **`@AllArgsConstructor`**：生成包含所有欄位的建構子。
    
      
    - **必要性**：**搭配 `@Builder` 時必須**。當使用了 `@Builder` 又使用了 `@NoArgsConstructor` 時，Java 會找不到全參建構子而報錯，必須加上 `@AllArgsConstructor` 才能正常編譯。
        
          
        

#### **JPA / Hibernate 註解**

- **`@Entity`**：將此類別標記為 JPA 實體，告訴 Spring / Hibernate 這是一個對應資料庫資料表的 Java 物件。
    
      
    - **必要性**：**完全必須**。沒有它 JPA 就不會掃描到這類別。
        
          
        
- **`@Table(name = "UP4_PROJECT_TASK_MEM")`**：指定此 Entity 對應到的資料庫資料表名稱。
    
      
    - **必要性**：如果 Java 類別名稱轉蛇形（`up4_project_task_mem_jpa_entity`）與實際資料表名稱完全一致，可省略；但**強烈建議保留**，能精準指定資料表名稱避免自動對映出錯。
        
          
        
- **`@EmbeddedId`**：標示此屬性為複合主鍵（嵌入式的 PK 物件）。
    
      
    - **必要性**：**完全必須**（因為使用了 `Up4ProjectTaskMemJpaEntityId` 複合主鍵）。
        
          
        
- **`@Column`**：用來指定 Java 屬性與資料庫欄位之間的對應關係（欄位名稱、長度、是否允許 Null 等）。
    
      
    - **必要性**：如果欄位名稱與變數名稱一致（如 `projectId` -> `PROJECT_ID`），可以省略；但為確保對齊 DDL 規範，**建議保留**。
        
          
        
- **`@ColumnDefault("0")`**：Hibernate 提供的註解，用於指定 **DDL 自動建表（`ddl-auto: update/create`）時的預設值**。
    
      
    - **必要性**：視情況而定（詳見問題 3）。
        
          
        

### 2. 為什麼有些欄位特別寫長度、nullable，有些不用？

這是因為 `@Column` 的屬性主要發揮在**兩個層面**：

  

1. **資料庫 Schema 自動生成（DDL Generation）**：
    
    當 `spring.jpa.hibernate.ddl-auto` 設定為 `update` 或 `create` 時，Hibernate 會依照 `@Column(length = 30, nullable = false)` 自動產出 SQL 指令（如 `VARCHAR2(30) NOT NULL`）。如果沒寫 `length`，預設會是 255；沒寫 `nullable`，預設是可以為 Null。
    
      
    
2. **Java 應用程式層級的欄位約束提醒**：
    
    明確寫出 `length = 30` 與 `nullable = false` 能讓後續維護程式碼的人直接一眼看出資料庫的 Schema 限制。
    
      
    

#### **為什麼 `isOwner` 沒有寫？**

- 布林值欄位（Boolean）在 SQL 中多半對應為 `NUMBER(1)`、`BIT` 或 `TINYINT`，其長度是固定的，因此不需要也不適合指定 `length`。
    
      
    
- 如果資料庫規範該欄位不能為 Null，依然建議加上 `nullable = false`。
    
      
    

### 3. 有預設值，就是用 `@ColumnDefault` 嗎？

**不完全是，而且 `@ColumnDefault` 常常無法達到你預期的效果！**

  

你需要了解 JPA 中處理預設值的 **兩種機制與差別**：

  

#### **機制 A：Java 物件層級預設值（最常用、最推薦）**

如果在建立物件時沒有指定 `isOwner`，你希望它預設為 `false`，直接在 **Java 變數賦予初始值** 是最直接且最安全的方式：

  

Java

```
@Builder.Default
@Column(name = "IS_OWNER")
private Boolean isOwner = false;
```

> 💡 **注意事項**：使用 `@Builder` 時，必須加上 **`@Builder.Default`**，否則透過 Builder 建立物件時，Java 的預設初始值（`false`）會被 Lombok 忽略而變成 `null`。
> 
>   

#### **機制 B：資料庫層級預設值（`@ColumnDefault`）**

`@ColumnDefault("0")` 是 Hibernate 專有的註解，它的作用**僅限於**：

  

1. **生成 DDL 時**，會在 `CREATE TABLE` SQL 中加上 `DEFAULT 0`。
    
      
    
2. **完全不會**影響 Java 物件剛 `new` 出來時的屬性狀態（在 Java 記憶體裡它依然是 `null`）。
    
      
    

如果你只寫了 `@ColumnDefault("0")`，在 Java 中寫 `repo.save(entity)` 時，若沒有設定 `isOwner`，Hibernate 發送的 SQL 依然會是 `INSERT INTO ... (IS_OWNER) VALUES (null)`，反而會把資料庫的預設值蓋掉！

  

### 💡 最終最佳實踐修復建議

結合上述討論與 JPA Entity 最佳實踐，建議重構為以下樣式：

Java

```
package com.flowring.up4.project.entity;

import jakarta.persistence.Column;
import jakarta.persistence.EmbeddedId;
import jakarta.persistence.Entity;
import jakarta.persistence.Table;
import lombok.AllArgsConstructor;
import lombok.Builder;
import lombok.Getter;
import lombok.NoArgsConstructor;
import lombok.Setter;
import org.hibernate.annotations.ColumnDefault;

@Getter
@Setter
@Builder
@NoArgsConstructor
@AllArgsConstructor
@Entity
@Table(name = "UP4_PROJECT_TASK_MEM")
public class Up4ProjectTaskMemJpaEntity {

    @EmbeddedId
    private Up4ProjectTaskMemJpaEntityId id;

    @Column(name = "PROJECT_ID", length = 30, nullable = false)
    private String projectId;

    @Builder.Default // 保障 Java Builder 建立時預設為 false
    @Column(name = "IS_OWNER", nullable = false)
    @ColumnDefault("0") // 保障 DDL 自動建表時有 DEFAULT 0
    private Boolean isOwner = false;

    // Getter 封裝（維持原本的 Convenience Helper 方法）
    public String getTaskId() {
        return id != null ? id.getTaskId() : null;
    }

    public String getMemId() {
        return id != null ? id.getMemId() : null;
    }
}
```


---
Lombok 的 **`@Builder`** 是一個用來實現 **建造者模式（Builder Pattern）** 的註解。

  

簡單來說，它的核心作用是：**讓你建立物件時，不必去記欄位的順序，也不用寫一堆 setter，能用像是「鏈式呼叫（Method Chaining）」的方式，寫出既清晰又好讀的程式碼**。

  

### 一、沒有使用 `@Builder` 的傳統寫法

假設要建立一個 Entity 物件，傳統有兩種方式：

  

#### 方式 1：使用全參建構子（Constructor）

Java

```
Up4ProjectTaskMemJpaEntity entity = new Up4ProjectTaskMemJpaEntity(id, "PRJ_2026_001", true);
```

- **缺點**：
    
      
    - 當欄位變多時（例如 10 個欄位），你根本記不住哪個參數要放在第幾個。
        
          
        
    - 如果有連續幾個相同型態（如連續 3 個 String），傳錯位置編譯器不會報錯，直接變成隱形 bug。
        
          
        

#### 方式 2：使用 Setter

Java

```
Up4ProjectTaskMemJpaEntity entity = new Up4ProjectTaskMemJpaEntity();
entity.setId(id);
entity.setProjectId("PRJ_2026_001");
entity.setIsOwner(true);
```

- **缺點**：
    
      
    - 程式碼顯得較為冗長。
        
          
        
    - 物件會處於「可變（Mutable）」狀態，無法確保物件建立時的完整性。
        
          
        

### 二、使用了 `@Builder` 後的寫法

加上 `@Builder` 之後，Lombok 會自動幫你產生一個內部的 Builder 類別，讓你這樣建立物件：

  

Java

```
Up4ProjectTaskMemJpaEntity entity = Up4ProjectTaskMemJpaEntity.builder()
        .id(id)
        .projectId("PRJ_2026_001")
        .isOwner(true)
        .build();
```

- **優點**：
    
      
    1. **欄位區分極度清晰**：每個值的前面都標明了欄位名稱（如 `.projectId(...)`）。
        
          
        
    2. **順序隨意**：你想先設 `projectId` 還是先設 `isOwner` 都可以。
        
          
        
    3. **可選欄位方便**：不想設的欄位直接不寫即可，不用傳 `null`。
        
          
        

### 三、關鍵細節：為什麼常跟 `@NoArgsConstructor` 與 `@AllArgsConstructor` 搭配？

這是在 JPA Entity 中使用 `@Builder` 最容易踩到的坑：

  

1. **JPA 的規定**：JPA 要求 Entity **必須有一個無參數建構子**（`@NoArgsConstructor`），這樣 Hibernate 才能透過反射幫你建立物件。
    
      
    
2. **Java / Lombok 的機制**：
    
      
    - 當你只寫 `@Builder` 時，Lombok 會自動幫你生成一個「全參建構子」。
        
          
        
    - 但一旦你手動加上了 `@NoArgsConstructor`，Java 就會以為你不需要全參建構子，導致 `@Builder` 找不到全參建構子而**編譯失敗**。
        
          
        

👉 **解決方法**：只要在 Entity 上**同時加上這三個註解**，就能完美兼容 JPA 與 Builder 模式：

  

Java

```
@Builder
@NoArgsConstructor  // 給 JPA 使用
@AllArgsConstructor // 給 @Builder 使用
@Entity
public class Up4ProjectTaskMemJpaEntity { ... }
```

### 四、關鍵細節：為什麼要有 `@Builder.Default`？

如果你在 class 中幫欄位寫了預設值：

  

Java

```
private Boolean isOwner = false;
```

- 如果用 **`new`** 或 **Setter**，`isOwner` 的預設值會是 `false`。
    
      
    
- 但如果用 **`@Builder`** 建立物件卻**沒有填寫 `isOwner`**，Lombok 會直接把它設為 **`null`**（忽略了你寫的 `= false`）！
    
      
    

👉 **解決方法**：告訴 Lombok 這個預設值要在 Builder 中生效：

  

Java

```
@Builder.Default
private Boolean isOwner = false;
```

這樣即使呼叫 `Up4ProjectTaskMemJpaEntity.builder().build()` 沒有傳入 `isOwner`，它也會安全地預設為 `false`。

答案是：**不完全是！欄位多時 `@Builder` 的效益最為顯著，但在單元測試與不可變（Immutable）設計中，即使欄位很少，`@Builder` 依然非常有價值。**

  

具體可以從以下 3 個實務情境來評估：

  

### 1. 單元測試（Unit Test）的最佳利器（即使欄位少也很實用）

在撰寫測試資料時，我們常常只需要指定「測試關心的特定欄位」，其他不相關的欄位希望它維持預設或 `null`。

  

- **使用傳統建構子**：如果你有 4 個欄位，只關心 `projectId`，你必須填滿所有參數：
    
      
    
    Java
    
    ```
    // 必須被迫帶入 null，程式碼可讀性極差
    var entity = new Up4ProjectTaskMemJpaEntity(id, "PRJ_001", null);
    ```
    
- **使用 `@Builder`**：可以只填有興趣的欄位，其他直接省略：
    
      
    
    Java
    
    ```
    var entity = Up4ProjectTaskMemJpaEntity.builder()
            .projectId("PRJ_001")
            .build();
    ```
    

### 2. 實現「不可變物件（Immutable Object）」

在 DDD 或乾淨架構（Clean Architecture）中，我們經常希望 **Domain Model** 或 **DTO** 建立後就「只讀不改」（不提供 `@Setter`，保障資料安全）。

  

- 當一個類別**完全沒有 Setter** 時：
    
      
    - **沒有 Builder**：只能透過龐大的建構子 `new MyDto(a, b, c, d)` 建立。
        
          
        
    - **有 Builder**：兼具「建構時的可讀性與彈性」以及「建構後的防篡改性（不可變）」。
        
          
        

### 3. 何時不需要或不適合使用 `@Builder`？

1. **欄位極少（1 ~ 2 個）且結構固定**：
    
    例如簡單的內嵌物件或小 DTO，直接用 `new` 或 Java 17 的 `record` 語法反而更簡潔：
    
      
    
    Java
    
    ```
    // 直接 new 簡單明瞭
    var role = new ProjectRoleResponse("ROL123", "會計");
    ```
    
2. **只有單一必填欄位的建構邏輯**：
    
    如果物件建立時必須強制同時傳入 `taskId` 與 `memId` 才能成立，用傳統建構子 `new Id(taskId, memId)` 能在**編譯時期就強制要求參數**，防範開發者漏設欄位；而 `@Builder` 預設無法在編譯期強制要求哪些欄位必填。
    
      
    

### 總結建議

- **Domain Model / DTO / Record**：建議廣泛使用（特別是 Record 或不可變物件）。
    
      
    
- **JPA Entity**：
    
      
    - **欄位 > 3 個**：強烈建議加上 `@Builder` + `@NoArgsConstructor` + `@AllArgsConstructor`。
        
          
        
    - **欄位 ≤ 3 個**：使用 `new` 或 `@Builder` 皆可，看團隊習慣。

---
這種設計採用了 **整潔架構 (Clean Architecture)** 或 **六角形架構 (Hexagonal Architecture / Ports and Adapters)** 的設計模式。

  

之所以拆分成這兩類，是為了達成「業務邏輯與框架（Spring Data JPA）解耦」的目的：

  

### 1. 藍框（SpringData...Repository）

- **角色**：**技術介面 (Spring Data JPA Interface)**
    
      
    
      
    
- **性質**：是一個 `interface`，繼承自 `JpaRepository`。
    
      
    
- **職責**：
    
      
    - 利用 Spring Data JPA 提供的魔法（如 `findBy...` 或 `@Query`），直接處理資料庫 CRUD 操作。
        
          
        
    - 它綁定的是 JPA 的 **Entity** 物件。
        
          
        
- **缺點**：如果核心業務直接依賴它，你的業務邏輯就會與 Spring Data JPA 這個框架強行綁定。
    
      
    

### 2. 紅框（...RepositoryAdapter）

- **角色**：**適配器 (Adapter Implementation)**
    
      
    
      
    
- **性質**：是一個 `class`，採用 **Adapter Pattern（適配器模式）**。
    
      
    
- **職責**：
    
      
    - **轉譯與隔絕**：內部注入藍框的 `SpringDataRepository`。
        
          
        
    - **模型轉換**：負責把 JPA 的 Entity 轉成業務層使用的 Domain Model（或相反）。
        
          
        
    - **實現領域介面**：它通常會實作一個獨立於框架的 `DomainRepository` 介面。
        
          
        

### 兩者互動架構示意圖

Plaintext

```
[ Service / 業務邏輯層 ] 
       │ 呼叫
       ▼
[ DomainRepository (介面) ]
       ▲
       │ 實作 (Implements)
[ Jpa...RepositoryAdapter (紅框 Class) ]
       │ 注入與呼叫 (Injects)
       ▼
[ SpringData...Repository (藍框 Interface) ]
       │ JPA
       ▼
[ Database ]
```

### 為什麼要這樣設計？（核心好處）

1. **職責分離 (SoC)**：核心業務邏輯只需要知道「如何存取資料」，不需要知道底層是用 Spring Data JPA、MyBatis 還是 JDBC。
    
      
    
2. **方便單元測試 (Unit Testing)**：Service 層測試時，只需 Mock 領域介面即可，不需要啟動 JPA 或 H2 資料庫。
    
      
    
3. **靈活性與可維護性**：如果未來團隊決定將資料庫改為 MongoDB 或 Redis，Service 層的程式碼**完全不需要修改**，只需要換掉紅框與藍框這層的實作即可。
