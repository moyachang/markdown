### 二、`common` 模組：問題主要是「定位不清」

依賴方向本身違規不多，`common` 沒有反向依賴 `up`、`af`、`dms`，這點是對的。真正的問題如下。

#### 🟠 問題 8：`common` 同時扮演四種角色

| 套件                                             | 實際角色                                     |
| ---------------------------------------------- | ---------------------------------------- |
| `domain/*`                                     | 共用 Domain（ExternalUser、MemConfig…）與 Port |
| `infrastructure/persistence/*`                 | 共用 JPA Entity 與 Repository 實作            |
| `security/*`、`xss/*`                           | Web 安全（Filter、Spring Security 設定）        |
| `utils/*`、`response/*`、`provider/*`、`shared/*` | 雜項工具與 API 回應包裝                           |

它的 `pom.xml` 也反映這一點：同時引入 `spring-boot-starter-web`、`data-jpa`、`security`、`oauth2-resource-server`、`shiro-core`，還有 `gson`、`json-lib`、`java-jwt`、`jjwt` 等多套 JSON/JWT 函式庫。**任何模組依賴 `common`，就等於把整包 Web + JPA + Security 一起拉進來**，連 Domain 的獨立性都談不上。

#### 🟠 問題 9：Domain 依賴 `utils`

`common/domain/exception/RRException` import 了 `common.utils.RespStatusEnum`，而且這個類別的 Javadoc 還寫著「不依賴任何框架（Domain Layer）」，實際上同時用了 Lombok 並依賴 utils。Domain 例外不該認識 HTTP 狀態碼列舉。

#### 🟠 問題 10：`utils` 反向依賴上層

`SNUtils` → `shared.PaseSerialNumberService`，`AfJwtUtils` → `provider.CorpProvider`。工具類別依賴 Service/Provider，表示它們根本不是「工具」，歸類有誤。

#### 🟡 問題 11：重複與測試殘留

- `RemoteServiceProvider` 有兩份（`common.domain.port` 與 `com.flowring.remoting`），`CompatibleRmiRemoteServiceProvider` 也有兩份，內容幾乎相同。你在程式註解裡已說明原因（外部 jar `wfci.jar` 綁定舊套件名稱），這個「橋接」是合理的，但建議明確標示為 legacy，並讓其中一份委派給另一份，避免兩份程式碼分頭修改。
- `domain/aggregate/Order`、`Actor`、`policy/CanApproveOrderPolicy` 都是 `@Deprecated` 且註明「測試用」，與業務無關，放在 `common.domain` 只會造成誤導，可以刪除。
- `common.infrastructure.persistence.repository.MemberRepository`（直接繼承 `JpaRepository`）與 `jpa/repository/` 底下那一整套 `SpringData*` 並存，是另一個「兩套擺法」。

#### 🟡 問題 12：其他模組直接用 `common` 的 SpringData Repository

`up` 的 `JpaMemberQueryRepositoryAdapter` 直接注入 `common` 的 `SpringDataExternalUserRepository`、`SpringDataMemGenInfRepository`、`SpringDataMemRolPathRepository`。這是「跨模組共用 infrastructure 內部實作」，一旦 `common` 改 Entity，`up` 會一起壞。

### 四、怎樣的設計最適合你？

你說主要是 DDD + Clean，偶爾混合六角形。這三者其實可以合併成同一套結構，**重點是用「Port 放在被依賴的那一側」這一個原則**統一起來。

#### 建議的目標結構（每個業務模組一份）

```
up/
├── adapter/                      ← 外部世界進來（Driving Adapter）
│   └── web/
│       ├── controller/
│       ├── dto/{request,response}/
│       └── mapper/               ← 只做「Application Result ⇄ Web DTO」
│
├── application/
│   ├── port/
│   │   ├── in/    (選用：UseCase 介面)
│   │   └── out/   ← 查詢用的 Port 放這裡（見下）
│   ├── command/                  ← 輸入（不是 Web Request）
│   ├── result/                   ← 輸出（不是 Web Response）
│   └── service/                  ← UseCase 實作，只認識上面三者 + domain
│
├── domain/                       ← 只依賴 JDK
│   ├── model/ (entity、vo、aggregate)
│   ├── repository/               ← 寫入用的 Repository 介面（聚合根）
│   └── service/
│
└── infrastructure/               ← 往外連（Driven Adapter）
    └── persistence/jpa/
        ├── entity/
        ├── repository/           ← SpringData + Adapter
        └── mapper/               ← JPA Entity ⇄ Domain / Row（從 adapter.web 搬來）
```

#### 四條規則（對應上面的問題）

1. **UseCase 只收 Command、只回 Result**（對應問題 1）  
    Web 的 Request/Response 與 MapStruct Mapper 只出現在 Controller。範例：

java

```java
   // Controller
   var result = useCase.execute(projectId);              // Application Result
   return ApiResponse.success(mapper.toResponses(result)); // Web Mapper 在這裡
```

2. **Port 介面簽章只能出現「自己這層或更內層」的型別**（對應問題 2、3、5）
    - 寫入用（Repository）：回傳/接收 Domain Entity 或 Aggregate，由 infrastructure 內的 Mapper 轉換 JPA Entity。
    - 查詢用（Query / 報表 / 列表）：Port 與 `RoleRow`、`MemberInfo` 這類讀取模型**一起放在 `application` 層**（`application/port/out` + `application/query`），因為它們本來就是為了 UseCase 而存在。這樣「Domain → Application」的反向依賴就消失了。
    - 分頁不要直接用 Spring 的 `Page`，自己定義簡單的 `PageResult<T>`，放在 application。
3. **轉換器跟著「產出的型別」所在的層走**（對應問題 4）
    
    |Mapper|該放哪裡|
    |---|---|
    |JPA Entity → Domain / Query Row|`infrastructure/persistence/jpa/mapper`|
    |Application Result → Web Response|`adapter/web/mapper`|
    |Web Request → Application Command|`adapter/web/mapper`|
    
4. **Domain 純粹化**（對應問題 5、9）  
    移除 `@Service`、`Page`、`StringUtils`；`LayoutDomainService` 的邏輯只是字串轉 boolean，可以改成 Command/Mapper 內的一行，或讓 Domain 用純 Java 寫。Spring 的標註留在 `application/service` 與 `infrastructure` 即可（Clean Architecture 實務上多半允許 UseCase 使用 `@Transactional`）。

#### `common` 該怎麼處理

最適合的做法是**拆成兩種性質不同的東西**，而不是一個大雜燴：

|新模組|放什麼|允許的依賴|
|---|---|---|
|`shared-kernel`（純 Java）|真正共用的 Domain 概念：`ExternalUser` 等 record、跨模組共用的 Port 介面、業務例外|只有 JDK|
|`platform` / `common-infra`（Spring）|Security、XSS、JWT、`ApiResponse`、共用 JPA Entity 與 SpringData|Spring、JPA 等|

並且遵守：

- `shared-kernel` 的例外**不帶 HTTP code**，HTTP 狀態碼在 `platform` 的 `RRExceptionHandler` 裡轉換。
- 各業務模組（`up`、`af`、`dms`）**透過 Port 使用共用資料**，而不是直接注入 `common` 的 `SpringData*Repository`。
- 工具類別（`utils`）只放無狀態的純函式；像 `SNUtils`、`AfJwtUtils` 這種依賴 Service 的，改成一般的 Spring Bean。

如果短期內不想拆 Maven 模組，至少先在**套件層級**拆開，並用下一節的測試守住邊界。

### 五、建議的行動順序（由小到大）

1. **先加 ArchUnit 測試**，把現況違規數量「凍結」（先允許既有違規，禁止新增），之後逐步清零。這是讓架構不再變亂的關鍵。
2. 修 `GetProjectRoleTreeUseCase`，把 Mapper 搬到 Controller，當作團隊範本。
3. 依同樣做法處理其他 UseCase（`GetProjectMembers…`、`GetManualPartnerUser…`、`GetMemberProfile…` 這幾個結構類似）。
4. 處理 JPA Entity 外洩：先從 `Up4ProjectTaskMem` 開始，建立 Domain 物件與 Mapper。
5. 把 `RoleRow`、`RoleMemberRow` 與 Query Port 移到 `application`。
6. 清掉 `Order`、`Actor`、`CanApproveOrderPolicy`、deprecated 的 `MemberInfo`、重複的 `RemoteServiceProvider`。
7. 最後才處理 `common` 的拆分。

ArchUnit 規則範例（可直接放進 `up` 的測試）：

java

```java
@AnalyzeClasses(packages = "com.flowring.up")
class ArchitectureTest {

    @ArchTest
    static final ArchRule layers = layeredArchitecture()
        .consideringOnlyDependenciesInLayers()
        .layer("Adapter").definedBy("..adapter..")
        .layer("Application").definedBy("..application..")
        .layer("Domain").definedBy("..domain..")
        .layer("Infrastructure").definedBy("..infrastructure..")
        .whereLayer("Adapter").mayNotBeAccessedByAnyLayer()
        .whereLayer("Application").mayOnlyBeAccessedByLayers("Adapter", "Infrastructure")
        .whereLayer("Domain").mayOnlyBeAccessedByLayers("Application", "Infrastructure", "Adapter")
        .whereLayer("Infrastructure").mayNotBeAccessedByAnyLayer();
}
```
