這是個很經典的設計取捨問題！讓我分析幾種方案的優劣：

## 常見方案比較## 三種策略分析

**策略一：回傳整個列表（最簡單）**

適合小列表、快速開發的情境。後端直接用新列表覆蓋，邏輯最簡單。缺點是 payload 隨列表大小線性增長，多人協作時容易發生「後來的人覆蓋前人」的問題。

**策略二：只回傳變動的那筆 + 新位置（整數 index）**

看起來合理，但實際上後端要把其他受影響的項目 index 全部位移（`UPDATE SET order_index = order_index + 1 WHERE ...`），複雜度仍是 O(n)，而且還是有並發衝突的問題。

**策略三：Fractional Indexing（最推薦）⭐**

這才是真正的最佳解。核心概念很簡單：

- 每個項目有一個浮點數 `order` 欄位
- 拖到兩個項目之間時，取前後兩個 `order` 的平均值
- 只需更新**一筆資料**，其他完全不動

```
PATCH /api/items/C
{ "order": 0.15 }  ← 就這樣，搞定
```

精度耗盡的問題（一直取中間、小數點越來越深）可以透過後台非同步的 `reindex` 來處理，使用者完全無感。

## 實務建議

如果你用的是字串排序（如 Notion、Linear 的做法），可以用 **LexoRank** 方案，效果一樣但用字串 key，不用擔心浮點精度問題。相關開源套件有 `lexorank`、`fractional-indexing`（JS/TS）可以直接用。

**兩端都可能用到，但核心邏輯通常在後端。**

**典型分工：**

- **後端** — 負責儲存、產生、更新 Fractional Index 的值，確保資料持久化與一致性
- **前端** — 在拖曳排序等互動時，可在本地先計算新的 index 值，達到即時反應的效果，再同步給後端

**實務上最常見的場景：** 前端拖曳排序 → 前端計算新的 Fractional Index → 送給後端儲存

所以嚴格來說，**計算邏輯前後端都需要理解**，但資料的最終維護責任在後端。

    public void rebalance(Long listId) {
        // 1. 撈出該清單所有項目，依目前順序排列
        List<Item> items = itemRepository
            .findByListIdOrderByFractionalIndex(listId);

        // "a1", "a2", "a3", "a4" ... 間距均勻

            String newIndex = generateEvenIndex(i, items.size());
            items.get(i).setFractionalIndex(newIndex);
        }

        // 3. 批次儲存
        itemRepository.saveAll(items);
    }

    private String generateEvenIndex(int position, int total) {
        // 平均分配，例如使用 "a0", "a1", "a2"... 重新起始
        return "a" + position;
    }
}

## 前端計算

`fractional-indexing` 套件核心只有一個函數 `generateKeyBetween(a, b)`：

```js
import { generateKeyBetween } from 'fractional-indexing'

// 初始列表
// A: "a0", B: "a1", C: "a2", D: "a3"

// 拖到最後面（後面沒有東西）
const newKey = generateKeyBetween("a3", null)
// → "a4"
```

## 唯一需要處理的例外：reindex

字串雖然理論上可以無限延伸，但現實中一直在同一個位置插入，key 會越來越長：

```
"a0" → "a0V" → "a0G" → "a0C" → "a0B" → "a0Bz" → ...
```

當長度接近你設定的 `varchar(255)` 或你自訂的閾值時，要觸發 reindex：

```js
// 後端收到 PATCH 後，順手檢查
async function updateOrder(itemId, newOrder) {
  await db.update(itemId, { order_key: newOrder })

  // key 太長時，非同步重新分配
  if (newOrder.length > 20) {
    triggerReindexAsync(listId)  // 不阻塞 response
  }
}

// reindex：把目前順序重新均勻分配
async function reindex(listId) {
  const items = await db.query(
    'SELECT id FROM items WHERE list_id = ? ORDER BY order_key ASC',
    [listId]
  )

  // 用套件產生均勻分布的 key
  let key = null
  for (const item of items) {
    key = generateKeyBetween(key, null)  // a0, a1, a2, a3 ...
    await db.update(item.id, { order_key: key })
  }
}
```

Reindex 是非同步背景執行，使用者完全無感。

### 1. 為什麼我們需要「分數索引」？

想像你有一個待辦事項列表：

1. 買牛奶
    
2. 倒垃圾
    

如果你想在兩者之間插入「洗衣服」，在傳統陣列中，你必須把「倒垃圾」的編號變成 3，這牽一髮動全身（如果列表有一萬筆，你要更新一萬筆資料）。

最直覺的解法是給新項目一個**小數（分數）**，變成這樣：

1. 買牛奶
    
    **1.5 洗衣服**
    
2. 倒垃圾
    

這就是「分數索引」的基本概念。但問題來了：如果你一直不斷地在兩個項目中間插入新東西（例如 `1.75`, `1.875`, `1.9375`...），JavaScript 的數字精確度（小數點後 52 位）很快就會被用光。一旦用光，系統就再也分不出誰先誰後了。

### 2. 作者的破解法：三大升級

為了突破系統數字精確度的極限，作者對「分數索引」進行了三次升級：

#### 升級一：用「字串」取代數字

作者決定完全放棄數學數字，改用**字串 (Strings)** 來表示小數點後面的數字。

- 原本的 `0.5` 變成字串 `"5"`
    
- 原本的 `0.75` 變成字串 `"75"`
    

**為什麼要這麼做？**

因為字串的比較是看「字典順序 (Lexicographical order)」。就像英文單字 Apple 會排在 Banana 前面一樣，字串 `"5"` 會永遠排在 `"75"` 前面。

只要你字串可以無限接下去寫（例如 `"7539485..."`），你就**永遠不會有精確度用完的一天**。

> **演算法的小巧思：** 作者特別寫了一個 `midpoint` (找中間值) 的演算法。當你想要在 `"5"` 和 `"1"`（代表結尾）之間插入時，傳統上會選正中間的 `"75"`，但作者的演算法會優先選 `"8"`。盡量保持字串簡短，節省儲存空間。

#### 升級二：換成 62 進位 (Base 62)

如果只用 `0~9` 這 10 個數字，字串長度還是會增加得有點快。

所以作者決定引入大小寫英文字母，變成 `0-9, A-Z, a-z`，總共 62 個字元。這就像是把原本的 10 線道高速公路拓寬成 62 線道，讓你可以插入極大量的資料，但字串長度依然能保持在短短幾個字元。

#### 升級三：終極大絕招「整數 + 分數」

文章後半段點出了一個致命問題：如果使用者不是在「中間插入」，而是單純一直**把新項目加在列表最底端**（Appending），分數索引會變成 `"9"`, `"99"`, `"999"`... 字串會無止盡地越來越長。

為了解決這個問題，作者的終極版索引把字串切成了兩半：**「整數部分」 + 「分數部分」**。

- **正常新增在尾端時：** 系統只會增加整數。作者發明了一套用字母開頭的整數寫法，例如第一個項目是 `a0`，第二個新增的是 `a1`，第三個是 `a2`。這樣不斷往後加，字串都不會變長。
    
- **在項目中間插入時：** 系統才會動用分數。例如你想在 `a1` 和 `a2` 之間插入，就會變成 `a1V`（`V` 就是前面說的 62進位中間值）。
    

為了確保字串排序不會亂掉（避免像 `"10"` 排在 `"2"` 前面的窘境），作者還設計了 `b00~bzz` 來代表比 `a` 更大的數字，以及 `Z0~Zz` 來代表負數（當你想把項目加在列表最上面時使用）。

在實作分數索引（Fractional Indexing）時，通常有兩種主要的底層編碼選擇：浮點數（Floating-Point Numbers）與字串字典序（Lexicographical Strings）。兩者各有其適用的場景與致命的缺陷。

以下為您詳細對比這兩者的優缺點：

## 1. 浮點數排序（Floating-Point Numbers）

這種方式直接使用資料庫或程式語言中的浮點數（如 `1.5`, `1.25`, `1.125`）來計算中間值：$\text{NewIndex} = \frac{A + B}{2}$。

- 優點：
    
    - 計算極其簡單：不需複雜的演算法，只需基本的加法與除法運算。
    - 儲存空間固定：在資料庫中（如 Float、Double），每個索引佔用的記憶體大小不變（通常為 4 或 8 位元組）。
    - 查詢效能極佳：資料庫對數字型態的索引排序和搜尋速度，遠快於字串型態。
    
- 缺點：
    
    - 快速退化（精度崩潰）：這是最嚴重的缺陷。由於計算機的二進位限制，當你在同一個位置連續插入物件約 50 到 60 次後，浮點數就會耗盡精度（出現 $\text{Underflow}$），導致新算出來的中間值與前後數值完全相同，排序系統直接失效。
    - 重平衡頻率極高：為了防止精度崩潰，系統必須非常頻繁地暫停服務，將整張列表的索引重新分配為整數（如 1, 2, 3）。

## 2. 字典排序（Lexicographical Strings）

這種方式將索引儲存為字串（如 `"a"`, `"n"`, `"z"`），並透過比較字元的 ASCII / Unicode 碼來決定先後順序。在中間插入時，會在字串尾端追加字元（如在 `"a"` 與 `"b"` 之間插入 `"am"`）。

- 優點：
    
    - 理論上接近無限插入：當字元空間不夠時（例如 `"a"` 和 `"b"` 之間想再插入），它可以直接在尾端增加一個字元變成 `"an"`。字串長度可以隨需求增長，因此極難遇到精度瓶頸。
    - 重平衡頻率極低：除非遇到極端的惡意操作，否則系統幾乎不需要進行全表重平衡，非常適合高頻率互動的協同編輯系統（如 Figma、Notion）。
    
- 缺點：
    
    - 索引長度膨脹（Spaghetti Strings）：如果使用者持續在同一個縫隙中插入物件，該物件的字串長度會變得越來越長（例如變成 `"amnzpq..."`），導致資料庫儲存空間和網路傳輸流量增加。
    - 字串比較效能較慢：資料庫在對字串進行 `ORDER BY` 排序時，效能明顯低於原生數字排序，當資料量極大時會拖慢查詢速度。
    - 實作複雜度高：要寫出一個能正確計算 `"az"` 與 `"b"` 之間中間值、且不會產生無效字元（如特殊符號）的字串演算法，邏輯相對繁瑣（通常需要依賴成熟的開源庫，如 `fractional-indexing`）。
