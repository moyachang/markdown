# JTDS vs Microsoft SQL Server 驅動：重複列異常處理分析

  

## 問題背景

  

同樣的 SQL 錯誤：`ALTER TABLE ART00121789453696604_Ins ADD ITEM9 varchar (100) NULL`

- **表中 ITEM9 列已存在**

  

## 觀察到的現象

  

### 使用 JTDS 驅動

```

2026-09-16 15:51:18:570 PerformanceMonitorInterceptor ERROR

- Exception SQL statement = [updateValue] ALTER TABLE ART00121789453696604_Ins ADD ITEM9 varchar (100) NULL

```

- ? 只記錄錯誤日誌

- ? **程式繼續運行，不拋出異常**

- ? 表中還是只有一個 ITEM9 列

  

### 使用 Microsoft SQL Server 驅動

```

Caused by: com.microsoft.sqlserver.jdbc.SQLServerException:

每個資料表中的資料行名稱必須是唯一的。資料表 'ART00121789453696604_Ins' 中的資料行名稱 'ITEM9' 指定了一次以上。

```

- ? 拋出 SQLServerException

- ? 程式中斷

- ? 業務操作失敗

  

## 根本原因

  

### 關鍵發現：異常捕獲與忽略

  

在 `ArtifactDaoJdbc.insertArtformItemInstanceColumn()` 第 1976-1988 行：

  

```java

public boolean insertArtformItemInstanceColumn(String table, VendorDependentDBSave dbSave, String columnType) {

    String sql;

    int index = columnType.toLowerCase().indexOf("null");

    sql = "ALTER TABLE " + table + " ADD " + dbSave.getColumnName() + " " + columnType;

    try {

        database.updateValue(sql);

    } catch (UncategorizedSQLException e) {

        // AF-8540 單一先跳過重複檢查

        // 不做事情 ← 異常被吞掉了！

    }

    return true;

}

```

  

**關鍵點**：只捕獲 `UncategorizedSQLException` 類型的異常！

```

```

```
  ↓ (Spring 轉換)

BadSqlGrammarException  ← 不匹配 UncategorizedSQLException ?

  ↓

異常繼續傳播

  ↓

業務層捕獲異常

  ↓

最終拋出給使用者

```

  

## Spring SQLErrorCodeSQLExceptionTranslator 的錯誤碼識別

  

Spring Framework 的異常轉換器會根據資料庫錯誤碼進行映射：

  

| 驅動程式 | 錯誤碼 | 錯誤類型 | Spring 異常類型 |

|---------|------|--------|----------------|

| MSSQL | 2705 | 重複的列名 | BadSqlGrammarException |

| JTDS | (類似) | 同上 | **UncategorizedSQLException** |

  

**為什麼 JTDS 被識別為 UncategorizedSQLException？**

  

1. **驅動程式版本差異**：JTDS 是第三方驅動程式，錯誤碼映射與 MSSQL Driver 不同

2. **錯誤資訊格式差異**：Spring 的 SQL 錯誤代碼轉換器可能無法準確識別 JTDS 的錯誤格式

3. **異常包裝方式不同**：JTDS 可能以不同的方式包裝 SQLException，導致 Spring 無法準確匹配

4. **容錯設計**：Spring 無法識別的錯誤 → 轉換為通用的 `UncategorizedSQLException`

## 為什麼會這樣設計？

  

代碼註解 "AF-8540 單一先跳過重複檢查" 表明這是**有意的容錯機制**：

  

```

場景：導入/升級表單結構時，列可能已存在

  

解決方案：

  1. 嘗試添加列（ALTER TABLE ADD）

  2. 如果列已存在 → 捕獲異常

  3. 繼續執行，不中斷流程

  4. 保持表結構完整

  

好處：

  ? 支援重複導入（冪等性）

  ? 支援增量更新

  ? 使用者友善

  

問題：

  ? 掩蓋真正的 SQL 錯誤

  ? 代碼 bug（如 ITEM9 重複）被異常捕獲隱藏了

  ? 只能通過日誌發現問題（JTDS 情況下）

  ? MSSQL 驅動異常無法被捕獲，導致程式中斷

```

## 完整的異常處理鏈路

  

### JTDS 驅動完整流程

```

1. 執行 SQL 語句

   ALTER TABLE ART00121789453696604_Ins ADD ITEM9 varchar (100) NULL

  

2. JTDS 檢測到錯誤

   "列已存在" 錯誤

  

3. JTDS 拋出 SQLException

  

4. Spring SQLErrorCodeSQLExceptionTranslator 處理

   ├─ 查找錯誤碼映射表

   ├─ JTDS 錯誤碼無法準確識別（第三方驅動程式）

   └─ 轉換為通用異常：UncategorizedSQLException

  

5. ArtifactDaoJdbc.insertArtformItemInstanceColumn() 捕獲

   catch (UncategorizedSQLException e)  ? 匹配

   └─ 異常被吞掉

  

6. 方法返回 true

   └─ 程式繼續運行

  

7. 但 PerformanceMonitorInterceptor 已經看到異常

   └─ 記錄日誌：Exception SQL statement = ...

```

  

### MSSQL 驅動完整流程

```

1. 執行 SQL 語句

   ALTER TABLE ART00121789453696604_Ins ADD ITEM9 varchar (100) NULL

  

2. MSSQL 驅動檢測到錯誤

   錯誤碼 2705："列名重複"

  

3. MSSQL 驅動拋出 SQLServerException

  

4. Spring SQLErrorCodeSQLExceptionTranslator 處理

   ├─ 查找錯誤碼 2705

   ├─ 找到對應映射："DuplicateColumn"

   └─ 轉換為特定異常：BadSqlGrammarException

  

5. ArtifactDaoJdbc.insertArtformItemInstanceColumn() 嘗試捕獲

   catch (UncategorizedSQLException e)  ? 不匹配

   └─ BadSqlGrammarException ≠ UncategorizedSQLException

  

6. 異常繼續向上傳播

  

7. PerformanceMonitorInterceptor 捕獲

   catch (Exception e) {

       logger.error("Exception SQL statement = ...");

       throw e;  ← 重新拋出

   }

  

8. 異常最終傳到業務層

   └─ 使用者看到異常

   └─ 程式中斷

```

  

## 我們的修復方案

  

**原則**：在源頭防止重複列的生成，而不是依賴異常捕獲

  

### 修復位置

1. `d:\WS_AF4\PASE\com\flowring\dao\jdbc\ArtifactDaoJdbc.java` ? 已修復

2. `d:\WS_AF4\PDE\objectbroker\iceDatabase.java` ? 已修復

  

### 修復方法

在 `createTableColumnScript()` 方法中添加去重邏輯：

  

```java

public StringBuffer createTableColumnScript(fcomponent.ColumnsHeaderNodeVector colVector) {

    StringBuffer createSQL = new StringBuffer();

    java.util.Set<String> processedColumns = new java.util.HashSet<String>();  // 新增

    for (int i = 0; i < colVector.size(); i++) {

        fcomponent.ColumnsHeaderNode node = colVector.get(i);

        VendorDependentDBSave dbSave = new VendorDependentDBSave(node, ...);

        String colID = node.getID();

        if (colID != null && !colID.equals("")) {

            String columnName = dbSave.getColumnName();

            // 新增：檢查重複列

            if (processedColumns.contains(columnName)) {

                logger.warn("Duplicate column name detected: " + columnName);

                continue;  // 跳過重複列

            }

            processedColumns.add(columnName);

            // 正常生成列定義...

        }

    }

    return createSQL;

}

```

## 總結

  

### JTDS 為什麼不拋出異常？

  

1. **異常被轉換**

   - JTDS 的 SQLException 被 Spring 轉換為 `UncategorizedSQLException`

  

2. **異常被捕獲**

   - 代碼故意捕獲 `UncategorizedSQLException`（AF-8540 容錯機制）

  

3. **異常被吞掉**

   - 方法返回 true，程式繼續運行

  

4. **日誌被記錄**

   - PerformanceMonitorInterceptor 記錄了異常發生

  

### MSSQL 為什麼拋出異常？

  

1. **異常被識別**

   - MSSQL 驅動的錯誤碼 2705 被 Spring 準確識別

  

2. **異常被轉換**

   - 轉換為 `BadSqlGrammarException`（不是 `UncategorizedSQLException`）

  

3. **異常不被捕獲**

   - 代碼的 catch 塊只捕獲 `UncategorizedSQLException`

  

4. **異常繼續傳播**

   - 異常向上傳播，最終拋給使用者

  

## 結論

  

這是 **Spring Framework 異常轉換機制** 和 **代碼設計的容錯機制** 相互作用產生的結果：

  

- **JTDS**：異常轉換為通用類型 → 代碼捕獲 → 程式繼續

- **MSSQL**：異常轉換為特定類型 → 代碼不捕獲 → 異常拋出

  

**正確的解決方案**：在源頭防止問題產生，不要依賴異常捕獲。? 我們已經實施了這個修復。
