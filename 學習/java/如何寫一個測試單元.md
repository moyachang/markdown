- 在對應的 test 位置 . application.service 建一個 test use case
-  ==由 Mockito 管理生命週期==
```java
	@ExtendWith(MockitoExtension.class) // 由 Mockito 管理生命週期   
```
		
- ==宣告 Mock 物件==
	- 在 
	- ```java
	  @Mock  
	  private ExternalUserRepository repository; // 宣告 Mock 物件
	  ```
- ==自動將 Mock 注入 use case==
- ```java
	@InjectMocks  
	private GetExternalUserUseCase useCase; // 自動將 Mock 注入此 UseCase
  ```
  - ==開始撰寫測試內容==
  - ```java
    @Test  
	@DisplayName("當使用者存在時，應成功回傳 ExternalUser 物件")  
	void returnsUserWhenFound() {
		// Arrange  
		String userId = "U1";  
		ExternalUser mockUser = createDummyUser(userId); // 取得自建的假資料  
		
		// 這裡做設定假行為，若有用到 findById，則回傳
		mockUserwhen(repository.findById(userId)).thenReturn(Optional.of(mockUser));  
	  
		// 真的執行 use case
		Optional<ExternalUser> result = useCase.execute(userId);  
	 
		// 做驗證:  
		// assertEquals: 檢查 result 是否等於 Optional.of(mockUser)
		assertEquals(Optional.of(mockUser), result);  
	  
		// verify: 驗證 Repository 方法確實有被呼叫，可確保 usecase 真的有去查 
		Repository.verify(repository).findById(userId);	
	}
    ```
- 其他的重點就是在要怎麼做驗證
- 簡單來說，就是針對
	- 針對 use case  執行的內容，做驗證。
	- 針對找不到 id
	- 針對找到 id，能否正確回傳。

同時 Mock 多個 Repository（或同一個 Repository 的多個不同方法）在單元測試中非常常見。不論您需要依賴多少個不同的 Repository，基本的 Mockito 核心邏輯都是一樣的：「宣告 Mock ➡️ 注入 Use Case ➡️ 逐一安排模擬行為 (when/then) ➡️ 執行與驗證 (verify)」。

為了讓您能直接看懂，我們直接以剛才提到的進階業務場景為例：

> 業務情境： 變更專案角色名稱時，不但要檢查角色是否存在，還要檢查「該專案內是否已存在相同的角色名稱」。為了示範「多個」Repository，我們假設這段邏輯還需要額外透過 `ProjectRepository` 來確認該專案是否處於「啟動狀態（Active）」。

以下是這個 Use Case 的進階實作，以及如何同時 Mock 三個技術點的單元測試寫法：

## 🧱 1. 進階版的 Use Case 實作

這個 Use Case 依賴了兩個不同的 Repository，並呼叫了三個不同方法：

```java
@Service
@RequiredArgsConstructor
public class RenameProjectRolUseCase {

    private final Up4ProjectRolRepository projectRolRepository;
    private final ProjectRepository projectRepository; // 💡 新增依賴

    @Transactional
    public void execute(RenameProjectRolCommand command) {
        // 1. 檢查角色是否存在 (來自 Up4ProjectRolRepository)
        Up4ProjectRol projectRol = projectRolRepository.findById(command.rolId())
                .orElseThrow(() -> new IllegalArgumentException("找不到指定的專案角色: " + command.rolId()));

        // 2. 檢查專案是否為 Active 狀態 (來自 ProjectRepository)
        boolean isProjectActive = projectRepository.isProjectActive(projectRol.getProjectId());
        if (!isProjectActive) {
            throw new IllegalStateException("該專案已被停用，無法修改角色名稱");
        }

        // 3. 檢查名稱是否在同專案內重複 (來自 Up4ProjectRolRepository 另一個方法)
        boolean isNameExists = projectRolRepository.existsByProjectIdAndRolName(
                projectRol.getProjectId(), command.newRolName()
        );
        if (isNameExists) {
            throw new IllegalStateException("該專案內已存在相同的角色名稱");
        }

        // 4. 變更並儲存
        projectRol.rename(command.newRolName());
        projectRolRepository.save(projectRol);
    }
}
```

## 💻 2. 同時 Mock 多個 Repository 的單元測試

在測試中，您只需要用 `@Mock` 宣告所有依賴的 Repository，Mockito 會自動幫您將它們全部注入（`@InjectMocks`）到 Use Case 中：

```java
package com.flowring.up.application.usecase;

import com.flowring.up.application.dto.command.RenameProjectRolCommand;
import com.flowring.up.domain.model.entity.Up4ProjectRol;
import com.flowring.up.domain.repository.ProjectRepository;
import com.flowring.up.domain.repository.Up4ProjectRolRepository;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import java.util.Optional;

import static org.junit.jupiter.api.Assertions.*;
import static org.mockito.Mockito.*;

@ExtendWith(MockitoExtension.class)
class RenameProjectRolUseCaseTest {

    // 💡 宣告多個 Mock，Mockito 會在記憶體中建立它們的虛擬代理物件
    @Mock
    private Up4ProjectRolRepository projectRolRepository;

    @Mock
    private ProjectRepository projectRepository;

    // 💡 Mockito 會自動將上面宣告的 projectRolRepository 和 projectRepository 
    //    同時注入到下面這個被測試的 Use Case 實例中
    @InjectMocks
    private RenameProjectRolUseCase renameProjectRolUseCase;

    @Test
    @DisplayName("當所有業務檢查都通過時，應成功修改名稱並儲存")
    void execute_AllChecksPass_Success() {
        // [1] Arrange - 準備測試資料
        String targetRolId = "role-123";
        String projId = "proj-001";
        String newName = "資深工程師";
        
        Up4ProjectRol existingRol = new Up4ProjectRol(targetRolId, projId, "工程師", "parent-001");
        RenameProjectRolCommand command = new RenameProjectRolCommand(targetRolId, newName);

        // [2] Arrangement - 同時 Mock 多個 Repository 的行為
        // 行為 A: 模擬尋找角色
        when(projectRolRepository.findById(targetRolId)).thenReturn(Optional.of(existingRol));
        
        // 行為 B: 模擬專案狀態檢查 (來自 ProjectRepository)
        when(projectRepository.isProjectActive(projId)).thenReturn(true);
        
        // 行為 C: 模擬名稱重複性檢查 (來自 Up4ProjectRolRepository)
        when(projectRolRepository.existsByProjectIdAndRolName(projId, newName)).thenReturn(false);

        // [3] Act - 執行測試
        renameProjectRolUseCase.execute(command);

        // [4] Assert - 驗證結果與多個 Repository 的互動流程
        assertEquals(newName, existingRol.getRolName());
        
        // 驗證流程：確認每個 Mock 物件的方法都有照預期被調用
        verify(projectRolRepository, times(1)).findById(targetRolId);
        verify(projectRepository, times(1)).isProjectActive(projId);
        verify(projectRolRepository, times(1)).existsByProjectIdAndRolName(projId, newName);
        verify(projectRolRepository, times(1)).save(existingRol); 
    }

    @Test
    @DisplayName("當專案已被停用時，應拋出異常且中斷後續的重複名稱檢查與儲存")
    void execute_ProjectNotActive_ThrowsException() {
        // Arrange
        String targetRolId = "role-123";
        String projId = "proj-001";
        Up4ProjectRol existingRol = new Up4ProjectRol(targetRolId, projId, "工程師", "parent-001");
        RenameProjectRolCommand command = new RenameProjectRolCommand(targetRolId, "新名稱");

        // 安排 Mock：
        when(projectRolRepository.findById(targetRolId)).thenReturn(Optional.of(existingRol));
        // 💡 故意讓專案回傳 false (已被停用)
        when(projectRepository.isProjectActive(projId)).thenReturn(false); 

        // Act & Assert
        IllegalStateException exception = assertThrows(IllegalStateException.class, () -> {
            renameProjectRolUseCase.execute(command);
        });

        assertEquals("該專案已被停用，無法修改角色名稱", exception.getMessage());

        // 核心驗證：因為在第二步就拋出異常，後續的「名稱重複檢查」與「儲存」絕對「不應該」被執行
        verify(projectRolRepository, never()).existsByProjectIdAndRolName(anyString(), anyString());
        verify(projectRolRepository, never()).save(any());
    }
}
```

## 🎯 多個 Mock 同時運作的核心思維

1. 不管是幾個不同 Repository，還是同一個 Repository 的不同方法：  
    只要在 Use Case 裡有被呼叫，您就必須在 `Arrange` 區塊中用 `when(...).thenReturn(...)` 把那條路徑「鋪好」。
2. 嚴格的順序與阻斷驗證：  
    如第二個測試案例所示，當我們模擬「專案停用（False）」時，程式應該在中途就崩潰。這時利用 `verify(..., never())` 去檢查後面那些本來需要被 Mock 的方法有沒有被偷跑，這能強烈確保您的業務邏輯「短路（Short-circuit）」機制運作正確。
